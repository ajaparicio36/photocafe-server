## Bouncy archive previews

Upload the silent, complete-frame MP4 as `bouncy_preview.mp4` through the existing
multipart `/api/upload` route, alongside original photos and printable stills.
Its lightbox plays inline, muted, automatically and on repeat, with pause controls.
Other MP4 and AVI files keep manual playback and their existing audio behavior.
Unsupported or damaged video exposes a download link; the archive download buttons
and ZIP remain available. File names and the eight-hour retention are unchanged.

The existing file route explicitly serves MP4 as `video/mp4` because `mime-types` 3
otherwise resolves it as `application/mp4`. Example (after uploading the archive):

```sh
curl -i http://localhost:3000/api/files/your-archive-id/bouncy_preview.mp4
# HTTP 200, Content-Type: video/mp4; the body is the original uploaded MP4.
```

Run `node scripts/check-archive-playback.cjs` for the Bouncy/legacy/still/PDF render
regression check, plus `npm run lint` and `npm run build`.
The route still returns complete files without byte-range support; production
payload sizes and camera output need separate verification.

### Local verification — 2026-10-18

The coordinating agent exercised a dedicated Chrome tab against the local
production build at `http://127.0.0.1:3017`. A synthetic silent H264 fixture
(620×922, six seconds, 897,501 bytes) represented a complete portrait sheet with
four quadrants; it was not generated by the booth application or a Canon camera.

- The new archive displayed the Bouncy MP4, printable still, original photo and
  legacy MP4 together. Bouncy playback started automatically. Captures more than
  six seconds apart showed the clock return to low timestamps, confirming repeat
  playback. The complete portrait composition fit a 1745×859 viewport.
- The legacy MP4 retained manual play; activating playback displayed its fixture
  frame. The invalid Bouncy fixture displayed the playback error and download link.
- Separate local HTTP checks uploaded all four attachments, listed and served
  them, downloaded each through the attachment route, and downloaded the ZIP.
  SHA-256 hashes matched the source bytes for individual and ZIP downloads.
- Build, lint and render regression checks passed; lint reported existing warnings.

The coordinating agent subsequently completed native-app → local upload → Chrome
verification using the application's generated rectangle test feed. The native
QR/archive view fit a 1266×713 viewport. Its archive contained ten actual app
outputs: `bouncy_preview.mp4`, `keychain_sheet.png`, four variant PNGs and four
original photo JPGs. Chrome displayed those attachments and automatically played
the silent, complete four-design sheet within a 1745×859 viewport. This exercised
the capture/composition/upload path rather than manually copying the MP4.

The resulting MP4 was H264, 620×922, six seconds, 36 decoded frames, 854,266 bytes,
with no audio stream. The still sheet was 1240×1844. Download through the existing
attachment route returned HTTP 200 and identical SHA-256 bytes. These are fixture
feed results; they do not establish real Canon capture quality or timing.

Mobile layout, production-sized payloads and physical camera fidelity remain
unverified. The error fallback uses the browser's
same-origin `download` attribute; forced attachment downloads are also available
through the archive's existing download buttons.

On 2026-10-20, build, lint, render regressions and local HTTP upload/list/serve/
attachment/ZIP checks passed again. Individual and ZIP attachment hashes matched
the synthetic source files. Interactive browser and camera QA was paused by the
user and was not repeated; the Chrome observations above are from 2026-10-18.
